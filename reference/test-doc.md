# 测试用例文档编写规范

让没看过 API 文档的人也能看懂。

## 文档结构

文档开头必须有 `## 系统简介` + `## 核心业务规则`。每个模块开头写接口说明 + 业务场景，并明确写出 `METHOD /path`；每个接口清单中的接口至少要在文档中出现一次。

## 每条用例必须包含

用例ID / 接口(方法+路径) / **接口用途**(最重要) / 前置条件 / 测试步骤 / 请求参数 / 预期结果(必须具体：状态码+字段值+错误码)

参数化用例加"参数化数据"字段，列出每个参数值 + 含义。

交付审计会按每个 `###` 用例块逐条检查：用例ID、接口、接口用途、前置条件、测试步骤、请求参数或请求体、预期结果都必须有非空内容；每个接口至少有一条用例。参数化测试可以用一条用例块加“参数化数据”覆盖多个 pytest node，但表中必须列出各组数据及含义。不要只堆关键词、空表或测试函数名。

## 反面示例

`| test_health_ok | GET /api/health | P0 | 返回 200 |` — 不知道接口干什么，预期太模糊。

## 正面示例

```markdown
> **接口说明**: `POST /api/orders` 创建订单，收取 0.5% 手续费。

### TC-O-001 下单成功

| 项目 | 内容 |
|------|------|
| **用例ID** | TC-O-001 |
| **接口** | `POST /api/orders` |
| **接口用途** | 验证下单成功且金额=单价×数量 |
| **前置条件** | 需要 token，余额充足 |
| **测试步骤** | 通过认证会话提交下单请求并检查响应 |
| **请求体** | `{"product_id":1, "price":100, "quantity":2}` |
| **预期结果** | 1. HTTP 201  2. total=200  3. fee=1.0 |
```
